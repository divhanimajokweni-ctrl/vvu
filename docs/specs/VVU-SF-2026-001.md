## 1. Scope and normative language

This specification defines the minimum shared contract that makes artefacts produced by one VVU environment parsable, integrity-checkable, and interpretable by another. It defines nothing else.

It does **not** define business logic, data stores, user interfaces, service topology, deployment configuration, or scheduling. Those remain the property of each environment.

### 1.1 Normative keywords

| Keyword | Meaning |
|---|---|
| **MUST** | Absolute requirement. Non-conformance is a defect. |
| **MUST NOT** | Absolute prohibition. |
| **SHOULD** | Recommended. Deviation requires a recorded reason in `limitations`. |
| **MAY** | Genuinely optional. No justification required. |

### 1.2 The independence rule

> Every environment MUST be able to complete its primary function with no other environment reachable and with no network connection.

Conformance to this document never overrides that rule. Where a requirement of this specification appears to conflict with independence, independence wins and the deviation is recorded in `limitations`.

### 1.3 What is shared and what is not

**Shared (this document):** the artefact envelope, the artefact type registry, the status vocabulary and transition rules, identity fields, digest and signature computation, version negotiation, the export package format, and the conformance test suite.

**Not shared:** everything else.

## 2. The artefact envelope

Every artefact that crosses an environment boundary MUST carry this envelope. The envelope is a wrapper. **The envelope never asserts that the content is true, verified, or correct.**

### 2.1 Field definitions

| Field | Type | Req | Definition |
|---|---|---|---|
| `envelope_version` | semver string | MUST | Version of this specification the producer conformed to. |
| `artefact_id` | UUID (RFC 9562 v4) | MUST | Stable identifier. Never reassigned, never reused. |
| `artefact_type` | enum (§3) | MUST | One of the seven registered types. |
| `produced_by` | object | MUST | Origin of the artefact (§2.2). |
| `produced_at` | RFC 3339 UTC timestamp | MUST | Production time, UTC, second precision minimum. |
| `content` | object | MUST | Type-specific payload (§3). |
| `provenance` | object | MUST | Lineage (§2.3). |
| `integrity` | object | MUST | Digest, optional signature and chain reference (§4). |
| `status` | enum (§5) | MUST | The producer's assessment at export. |
| `limitations` | array of strings | MUST | Known limits. MAY be empty, except where §5.4 forbids it. |

Additional fields MUST NOT be added at the top level. Environment-specific data belongs in `content` or `provenance.configuration`.

### 2.2 `produced_by`

```
produced_by:
  environment:    enum    forge | bench | fire | field | press
  instance_id:    string  unique per running instance, stable across its lifetime
  operator_id:    string  accountable human or service identity
  software_version: semver
```

- `environment` MUST be exactly one of five values. Values MUST NOT be combined or invented.
- `instance_id` MUST be unique among concurrently live instances of that environment.
- `operator_id` MUST identify an accountable party. Anonymous production is forbidden.

### 2.3 `provenance`

```
provenance:
  inputs:       array<UUID>   upstream artefact_ids. MAY be empty.
  supersedes:   array<UUID>   artefact_ids this one replaces. MAY be empty.
  policy:       string        verification policy identifier, when applicable
  configuration: string       configuration or model identifier, when applicable
```

- `inputs` lists the artefacts this one was derived from. Empty is valid and common.
- `supersedes` declares replacement. Setting it MUST NOT modify the superseded artefact (see §7).
- `policy` MUST be present when `artefact_type` is `verification_receipt`.
- `configuration` SHOULD be present when the artefact's content depends on a versioned configuration.

## 3. Artefact type registry

Seven types. The list is closed. A new type requires a new minor version of this specification and a migration note.

| Type | Producer | Content schema |
|---|---|---|
| `claim` | Forge | `{ statement, scope, basis, assumptions[] }` |
| `model` | Forge | `{ model_id, model_type, parameters_ref, code_ref, inputs[], outputs[] }` |
| `learning_submission` | Forge | `{ module_id, exercise_id, response, submitted_at }` |
| `experimental_record` | Forge | `{ experiment_id, hypothesis, method, configuration, raw_results, observed_at }` |
| `validation_payload` | Forge | `{ harness_id, harness_version, seed, configuration, outcome, output_ref }` |
| `observation` | Field | `{ value, unit, sensor_id, measured_at, received_at, sensor_state, calibration_state, location }` |
| `verification_receipt` | Bench | `{ claim_ref, policy, evidence_refs[], checks[], outcome, scope_statement, limitations[] }` |
| `test_report` | Fire | `{ target_ref, threat_model_ref, cases[], summary, counterexample_refs[] }` |
| `counterexample` | Fire | `{ target_ref, failure_ref, minimal_reproduction, conditions, expected, actual }` |
| `publication` | Press | `{ title, body_ref, referenced_artefacts[], approvals[], version, corrections[] }` |
| `status_transition` | any | see §5.5 |

> **Note.** The parent blueprint lists seven types. This specification registers **ten** plus the status-transition record, because Forge's harness output, Fire's two output types, and Bench's receipt each require distinct content schemas that cannot be collapsed without losing meaning. This is recorded as deviation **D-01** (§9). The transition record is a record, not an artefact type, and is defined in §5.5.

### 3.1 Type-specific required content

**`observation`** — Field MUST populate every field. Where a value is unavailable:

- `sensor_state` ∈ `NOMINAL | DEGRADED | FAULT | UNKNOWN`. An observation from a faulty sensor MUST still be recorded; it MUST NOT be silently dropped.
- `calibration_state` ∈ `VALID | EXPIRED | UNKNOWN`.
- `measured_at` and `received_at` MUST both be present. Their difference is the transmission latency and is evidentially relevant.

**`verification_receipt`** — Bench MUST populate `checks[]` with one entry per check performed, each `{ check_id, description, result, evidence_ref }`. `outcome` MUST be one of `VERIFIED | INCONCLUSIVE | NOT_PROVEN | BLOCKED`. `scope_statement` MUST state what the receipt does and does not establish.

**`test_report`** — Fire MUST record every case with `{ case_id, threat_ref, expected, actual, result }` where `result` ∈ `PASS | FAIL | BLOCKED | NOT_RUN`. A case that could not execute MUST be recorded as `BLOCKED` or `NOT_RUN` with a reason. It MUST NOT be recorded as `PASS`.

**`publication`** — Press MUST list every referenced artefact in `referenced_artefacts[]` and MUST record each approval in `approvals[]` as `{ approver_id, approved_at, approved_version }`.

## 4. Integrity: digest and signature

### 4.1 Canonical serialisation

All digest and signature computation operates on **JSON Canonicalization Scheme (JCS, RFC 8785)** serialisation of the relevant object. Implementations MUST use a conforming JCS serializer. Any other serialisation produces a non-interoperable digest.

JCS sorts object keys lexicographically by UTF-16 code unit and removes insignificant whitespace. Field order in this document is therefore presentational and has no effect on any computed digest.

### 4.2 Digest

```
digest = "sha256:" + lowercase_hex(SHA256(JCS(envelope_without_integrity)))
```

- `envelope_without_integrity` is the complete envelope object with the `integrity` key removed.
- The digest therefore covers `envelope_version`, `artefact_id`, `artefact_type`, `produced_by`, `produced_at`, `content`, `provenance`, `status`, and `limitations`.
- The prefix `sha256:` is mandatory. The hex is 64 lowercase characters.
- A missing digest is a conformance failure. Digests are **not** optional in this specification.

### 4.3 Signature

```
signature = "ed25519:" + base64url_nopad(Ed25519_sign(private_key, raw_digest_bytes))
```

- The signed message is the **32 raw digest bytes**, not the hex string and not the prefixed string.
- `base64url_nopad` is base64url per RFC 4648 §5 with `=` padding removed.
- The verifying key MUST be resolvable from the signing identity. How keys are published is each environment's concern; this specification only requires that a receiver can resolve the key or return `REJECTED_SIGNATURE_UNRESOLVED`.
- Signature is **optional**. An unsigned artefact is valid; it simply carries no producer authentication.

### 4.4 Chain reference

`integrity.chain_ref` is an optional reference into the WORM ledger maintained by Bench. It is a pointer, not a proof. Presence of `chain_ref` does not imply the artefact was verified, and absence does not imply it was not.

### 4.5 Verification order

A receiver MUST perform integrity checks in this order and MUST stop at the first failure:

1. Parse `envelope_version`; apply §6.
2. Validate against the JSON Schema.
3. Recompute the digest; compare to `integrity.digest`.
4. If a signature is present, resolve the key and verify.
5. Only then consider `status`.

A signature over a digest that does not match the content is a failure at step 3, not step 4.

## 5. Status vocabulary and transitions

### 5.1 The vocabulary

Twelve values. Same words, same meaning, in every environment.

| Status | Meaning |
|---|---|
| `DRAFT` | Created locally. Not yet exported. |
| `IMPORTED` | Received by a receiving environment. Structure not yet checked. |
| `PARSED` | Structure understood. Content not yet validated. |
| `INTEGRITY_VALID` | Digest matches; signature valid if present. |
| `VERIFIED` | Applicable verification policy satisfied. |
| `INCONCLUSIVE` | Checked; the evidence does not establish the result. |
| `NOT_PROVEN` | Mandatory conditions not satisfied. |
| `REJECTED` | Refused for a stated reason. |
| `BLOCKED` | A required operation could not proceed. |
| `EXPIRED` | Time-bounded validity has passed. |
| `SUPERSEDED` | A newer artefact replaces this one's authority. |
| `WITHDRAWN` | Producer has retracted it. |

### 5.2 Allowed transitions

`—` means no transition is defined. Transitions not listed are forbidden.

| From | To |
|---|---|
| `DRAFT` | `IMPORTED` |
| `IMPORTED` | `PARSED`, `REJECTED` |
| `PARSED` | `INTEGRITY_VALID`, `REJECTED` |
| `INTEGRITY_VALID` | `VERIFIED`, `INCONCLUSIVE`, `NOT_PROVEN`, `REJECTED`, `BLOCKED` |
| `VERIFIED` | `EXPIRED`, `SUPERSEDED`, `WITHDRAWN` |
| `INCONCLUSIVE` | `VERIFIED`, `NOT_PROVEN`, `EXPIRED`, `SUPERSEDED`, `WITHDRAWN` |
| `NOT_PROVEN` | `VERIFIED`, `INCONCLUSIVE`, `EXPIRED`, `SUPERSEDED`, `WITHDRAWN` |
| `BLOCKED` | `PARSED`, `INTEGRITY_VALID`, `VERIFIED`, `INCONCLUSIVE`, `NOT_PROVEN`, `EXPIRED`, `WITHDRAWN` |
| any | `REJECTED` |
| any | `EXPIRED`, `SUPERSEDED`, `WITHDRAWN` |

Rules:

- `DRAFT → IMPORTED` is the only transition out of `DRAFT`. An artefact either stays a draft or crosses a boundary.
- **Skipping is forbidden.** `PARSED` MUST NOT become `VERIFIED` directly. Integrity must be established first.
- **Backwards movement is forbidden** except from `BLOCKED`, which is a stall rather than a failure.
- `REJECTED`, `EXPIRED`, `SUPERSEDED`, and `WITHDRAWN` are terminal. Nothing leaves them.
- `VERIFIED` is the strongest status and requires a policy check. It is never assigned by an integrity check.

### 5.3 What the statuses mean and do not mean

- `NOT_PROVEN` does not mean false. It means not established. It is a substantive finding and requires a reason.
- `INCONCLUSIVE` means the available evidence was insufficient to decide. It requires a statement of what was missing.
- `REJECTED` is a processing failure. `NOT_PROVEN` is a finding. They are not interchangeable.
- `BLOCKED` means a dependency was unavailable. It MUST NOT be recorded as a negative result. A receiver MUST distinguish "the check failed" from "the check could not run."

### 5.4 `limitations` requirements

`limitations` MUST be non-empty when `status` is `INCONCLUSIVE`, `NOT_PROVEN`, or `BLOCKED`. It MUST state what is missing, unverified, or out of scope.

`limitations` SHOULD be non-empty for `VERIFIED` when the verification policy has a narrower scope than the claim it was checked against. This is the mechanism that prevents a receipt from being read as broader than it is.

### 5.5 The status-transition record

`envelope.status` is the producer's assessment at export and is **immutable**. A receiver MUST NOT modify a received artefact to record a new status. Instead it records a transition:

```
status_transition record:
  artefact_id:     UUID       the artefact whose status changed
  from_status:     enum       previous status
  to_status:       enum       new status, per §5.2
  transitioned_at: RFC 3339   UTC
  actor:
    environment:   enum
    instance_id:   string
    operator_id:   string
  reason_code:     string     required when to_status is REJECTED, INCONCLUSIVE,
                              NOT_PROVEN, or BLOCKED — see §5.6
  basis:           string     what was done to justify the transition
  limitations:     array<string>
```

The record is enveloped with `artefact_type: status_transition`, its own `artefact_id`, its own digest, and SHOULD be signed by the transitioning party. It is exported with `status: VERIFIED` only when the transition itself has been checked; otherwise `PARSED`.

A receiver's current view of an artefact is therefore: *(exported status)* followed by *(the ordered list of transition records referencing it)*.

### 5.6 Reason-code registry

Codes are stable. New codes are appended; existing codes are never renumbered or repurposed.

| Code | Applies to | Meaning |
|---|---|---|
| `REJECTED_VERSION_UNSUPPORTED` | REJECTED | `envelope_version` outside the receiver's supported set (§6). |
| `REJECTED_SCHEMA_INVALID` | REJECTED | Envelope or content failed schema validation. |
| `REJECTED_TYPE_UNKNOWN` | REJECTED | `artefact_type` not in the registry. |
| `REJECTED_DIGEST_MISMATCH` | REJECTED | Recomputed digest differs from `integrity.digest`. |
| `REJECTED_SIGNATURE_INVALID` | REJECTED | Signature present and failed verification. |
| `REJECTED_SIGNATURE_UNRESOLVED` | REJECTED | Signing key could not be resolved. |
| `REJECTED_POLICY_UNSUPPORTED` | REJECTED | Named policy not supported by the receiver. |
| `REJECTED_UNAUTHORIZED` | REJECTED | Actor not permitted to submit. |
| `REJECTED_DUPLICATE` | REJECTED | `artefact_id` already received with different content. |
| `REJECTED_SCOPE_EXCEEDED` | REJECTED | Request exceeds the actor's authorised scope. |
| `INCONCLUSIVE_EVIDENCE_MISSING` | INCONCLUSIVE | Named evidence artefact unavailable. |
| `INCONCLUSIVE_EVIDENCE_INSUFFICIENT` | INCONCLUSIVE | Evidence present but does not support a determination. |
| `NOT_PROVEN_CONDITION_UNMET` | NOT_PROVEN | A mandatory condition of the policy was not satisfied. |
| `NOT_PROVEN_CONTRADICTED` | NOT_PROVEN | Evidence contradicts the claim. |
| `BLOCKED_DEPENDENCY_UNAVAILABLE` | BLOCKED | A required service or environment was unreachable. |
| `BLOCKED_INPUT_INCOMPLETE` | BLOCKED | Required input not yet supplied. |
| `EXPIRED_VALIDITY_PASSED` | EXPIRED | Time-bounded validity elapsed. |
| `SUPERSEDED_BY_NEWER` | SUPERSEDED | A newer artefact declared `supersedes`. |
| `WITHDRAWN_BY_PRODUCER` | WITHDRAWN | Producer retracted. |

## 6. Version negotiation

### 6.1 Supported versions

Every environment MUST declare the set of `envelope_version` values it supports, as a published, machine-readable list.

### 6.2 On receive

1. Read `envelope_version` from the incoming artefact.
2. If it is in the supported set, accept and continue.
3. If it is not, reject with `REJECTED_VERSION_UNSUPPORTED`, stating the version received and the versions supported.
4. If it is a **newer minor within the same major**, accept with `status: IMPORTED` and record the mismatch in `limitations`.
5. If it is a **newer major**, reject. Do not guess at semantics.

### 6.3 The non-upgrade rule

> A version match MUST NOT raise the trust status of an imported artefact.

Version negotiation governs *parseability*, never *truth*. An artefact from a supported version arrives as `IMPORTED` and earns each subsequent status only by performing the corresponding check.

### 6.4 Producer obligation

A producer MUST NOT emit an `envelope_version` it does not conform to. Emitting a newer version to appear current is a conformance failure.

## 7. Immutability and supersession

- An exported artefact MUST NOT be modified. Correction is by supersession, never by mutation.
- `provenance.supersedes` on artefact *B* naming artefact *A* means *B* replaces *A*'s authority. *A* is then `SUPERSEDED`. *A* itself is unchanged and remains retrievable.
- `SUPERSEDED` is recorded as a transition on *A*, with `reason_code: SUPERSEDED_BY_NEWER` and *B*'s `artefact_id` in `basis`.
- Both *A* and *B* MUST remain retrievable. Supersession preserves history; it does not delete it.

## 8. Export package format

Because an environment must be able to hand its work onward with no other environment online, export MUST be self-contained.

```
export_package:
  package_version:  "1.0"
  exported_at:      RFC 3339 UTC
  exported_by:
    environment:    enum
    instance_id:    string
    operator_id:    string
  manifest:
    artefact_count: integer
    artefacts:
      - artefact_id:   UUID
        artefact_type: enum
        digest:        "sha256:..."
        status:        enum
  artefacts:        array<envelope>
  package_digest:   "sha256:..."   SHA256 over JCS(manifest)
```

Rules:

- Every `artefact_id` in `artefacts[]` MUST appear in `manifest.artefacts[]` and vice versa.
- `package_digest` covers the manifest only, so a receiver can detect manifest tampering without parsing every artefact.
- Artefacts are exported in their exported status. A package MUST NOT relabel an artefact's status to make it look better.
- A package MUST be importable by an environment that has never seen the producing environment before, using only this specification.

## 9. Deviations from the parent blueprint

Recorded openly, per the zero-fabrication rule.

| ID | Deviation | Reason |
|---|---|---|
| **D-01** | Artefact type registry expanded from 7 to 10. | Forge harness output, Fire's `test_report` and `counterexample`, and Bench's receipt have distinct content schemas that cannot be collapsed without losing meaning. `counterexample` and `test_report` are Fire's two outputs and cannot share a schema. |
| **D-02** | Digest made mandatory rather than "always present in practice." | A shared foundation permitting digest-less artefacts cannot guarantee integrity across boundaries. |
| **D-03** | `envelope.status` made immutable; transitions moved to a separate record. | The parent design places mutable status inside a signed envelope. Updating status would invalidate the producer's signature. The transition record preserves both immutability and the status pipeline. |
| **D-04** | Reason-code registry added. | The blueprint requires a "stated reason" for `REJECTED` but defines no vocabulary. Without codes, reasons are prose and cannot be tested. |

## 10. Per-environment failure declaration

Each environment MUST publish answers to these four questions in its own specification, in this shape. Failure to answer any one disqualifies that environment from being counted as independent.

```
failure_declaration:
  environment: enum

  offline_capability:
    primary_function_offline: boolean     MUST be true
    degraded_functions: array<string>
    local_persistence: string

  dependency_unavailability:
    distinguishes_unavailable_from_negative: boolean   MUST be true
    unavailable_status: enum             MUST be BLOCKED
    behaviour: string

  recovery:
    unfinished_work_preserved: boolean   MUST be true
    interrupted_operations_recorded: boolean  MUST be true
    resume_safety: string

  portability:
    export_path_exists: boolean          MUST be true
    export_requires_other_environment: boolean  MUST be false
    export_format: string                MUST reference §8
```

## 11. Conformance test suite

Each test is independently checkable. An implementation conforms only if it passes all applicable tests. `Fire` is the natural executor of this suite.

### 11.1 Envelope and schema

| ID | Assertion |
|---|---|
| CF-01 | An artefact missing any MUST field is rejected with `REJECTED_SCHEMA_INVALID`. |
| CF-02 | An artefact with a top-level field outside §2.1 is rejected with `REJECTED_SCHEMA_INVALID`. |
| CF-03 | `produced_by.environment` outside the five values is rejected with `REJECTED_TYPE_UNKNOWN`. |
| CF-04 | Two artefacts from the same producer have different `artefact_id` values. |
| CF-05 | An `artefact_id` is never reused for different content; a repeat with different content is `REJECTED_DUPLICATE`. |
| CF-06 | `artefact_type` outside the registry is rejected with `REJECTED_TYPE_UNKNOWN`. |
| CF-07 | Every `provenance.inputs[]` entry resolves to a known `artefact_id` or is absent; unresolved references are recorded in `limitations`, not silently dropped. |

### 11.2 Digest and signature

| ID | Assertion |
|---|---|
| CF-08 | Recomputing the digest per §4.2 over a conforming artefact reproduces `integrity.digest` exactly. |
| CF-09 | Altering any single byte of `content` changes the digest, and the artefact is rejected with `REJECTED_DIGEST_MISMATCH`. |
| CF-10 | Altering `status`, `limitations`, `produced_at`, or `provenance` changes the digest. |
| CF-11 | A signature computed over the raw digest bytes verifies; one computed over the hex string does not. |
| CF-12 | An artefact whose signature fails verification is rejected with `REJECTED_SIGNATURE_INVALID`. |
| CF-13 | An artefact whose signing key cannot be resolved is rejected with `REJECTED_SIGNATURE_UNRESOLVED`. |
| CF-14 | A digest over a non-JCS serialisation does not match. |

### 11.3 Status and transitions

| ID | Assertion |
|---|---|
| CF-15 | `PARSED → VERIFIED` is refused. |
| CF-16 | Every transition out of a terminal state is refused. |
| CF-17 | `BLOCKED` is never recorded as `NOT_PROVEN` or `INCONCLUSIVE`. |
| CF-18 | `INCONCLUSIVE`, `NOT_PROVEN`, and `BLOCKED` always carry a non-empty `limitations` and a `reason_code`. |
| CF-19 | An integrity check never assigns `VERIFIED`. |
| CF-20 | A version match alone never produces `VERIFIED`. |
| CF-21 | A superseded artefact remains retrievable and unchanged. |
| CF-22 | Updating an artefact's status in place is impossible; the receiver records a transition instead. |

### 11.4 Version negotiation

| ID | Assertion |
|---|---|
| CF-23 | An unsupported major version is rejected with `REJECTED_VERSION_UNSUPPORTED`. |
| CF-24 | A newer minor within the same major is accepted with the mismatch recorded in `limitations`. |
| CF-25 | A supported version is accepted and arrives as `IMPORTED`. |

### 11.5 Export and portability

| ID | Assertion |
|---|---|
| CF-26 | An export package produced with no network and no other environment online is importable by a conforming receiver. |
| CF-27 | `package_digest` detects a modified manifest. |
| CF-28 | `manifest.artefacts[]` and `artefacts[]` have identical `artefact_id` sets. |
| CF-29 | Exported statuses match the producer's actual assessment; no relabelling. |

### 11.6 Independence

| ID | Assertion |
|---|---|
| CF-30 | Each environment completes its primary function with all other environments unreachable. |
| CF-31 | Each environment publishes a `failure_declaration` per §10 with all four `MUST be true` / `MUST be false` flags satisfied. |
| CF-32 | Field captures and queues observations with no connectivity, and the queue survives a restart. |

## 12. Change control

| Change | Required |
|---|---|
| New reason code | Append to §5.6. Minor version. |
| New artefact type | New minor version, migration note, new content schema, conformance tests. |
| New status value | New major version. Status vocabulary is the load-bearing shared contract. |
| Digest algorithm change | New major version. All prior digests become unverifiable by conforming receivers and MUST be recorded as such. |
| Removing a field | New major version. |

**No change is applied retroactively.** Artefacts already exported keep the version they were exported with and remain interpretable by receivers that support that version.
